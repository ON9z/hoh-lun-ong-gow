# 机制自我服务率 —— 一个长期自动化系统的机制，会**吃掉全部产能**，而**每条守卫都报绿**

判据：**「最近 N 笔产出里，有多少笔触及了【这个系统存在的目的】？」**
⚠ **答不出 / 趋近 0** ⇒ ⭐ **机制在自转** —— ⚠ 而**这不是任何一条守卫的失效**：
**因为根本没有任何守卫在量「力气花到哪了」**。

**⇒ 为什么**：守卫按定义只检查**某个不变量**（账本是诚实的 / 文档与现实一致 / 文件名卫生）。
⭐ **它们全是【局部】的判据** ⇒ 每一条都可以在自己的范围内**永远为真**，
⚠ 而**整体的产能可以 100% 流向机制自身** —— **没有任何一条会红**。
⚠ 更坏的是：**机制越完善，它需要维护的表/账本/清单就越多** ⇒
⇒ **这个方向是【自催化】的**：机制产出的每一样东西，都变成机制下一步要维护的对象。

⚠ **⚠ 而它极难被发现，因为它【每一步看起来都在工作】**：
每一轮都有产出（提交、报告、审计、修复），**每一份产出都真实且有用**，
⭐ 只是**它们服务的对象是机制自己**。

**实例（单人-单机自动化系统，2026-09-29 实测）**：
用户问「**该不该有这么多闸（个人认为有缺陷）**」。⭐ 我先去量了闸本身：
**12 条闸 = 5 个不变量族，无一条是另一条的重复**（每条都对应一个**不同的**已记录事故）
⇒ ⭐ **缺陷不在【闸的数量】**。

⚠ 那我该量什么？⭐ 量**最近 60 笔提交（4.4 小时内）**：

| 类别 | 笔数 |
|---|---|
| 机制自身（守卫/钩子/交接锚点/索引/外部咨询/自查/设计文档/审计快照） | **~50（83%）** |
| 任务域（数据管道修复 · 回填核对 · 口径决策） | ~10（17%） |
| ⭐⭐ **该系统存在的目的**（产出真正的业务结果） | **0** |

⭐⭐ **结论**：**缺陷不在闸的数量，在于【没有任何一条闸在量这句话】**。
⚠ 而且**写出这条准则的这一轮本身**，就是又一个机制轮次：**40 分钟，0 笔业务产出**。

**⇒ 做法**：

① **建一个【产出构成】计量器**，⛔ 不建闸：
   按路径/标题把最近 N 笔产出分类，打出**每一类的占比**。
   ⚠ **⛔ 不要把它接进提交钩子** —— ⭐ 那等于**再加一条守卫**，与「给机制减负」**反向**。
   它以**诊断器**形态存在：**手动跑，或每轮收口时跑一次**。
② **判据要写成【不依赖阈值】的形状**：
   ⚠ 「机制占比 > 0.7 ⇒ 红」**看起来**像一个判据，但它**是一条浮动的线**（实测 0.67 距它只差 2 笔）。
   ⭐ 改用**二值的事实**：「**本窗口产出的【业务结果】= 0 笔**」—— ⚠ 它**不含任何可调的参数**。
③ **⚠ 计量器本身也要披露它的软处**：按关键词分类**分不清「提到」与「产出」**
   （实测：唯一一笔「含业务词」的提交是**一份提到该词的文档订正**，⛔ 它不产出任何结果）
   ⇒ ⭐ **报数字时必须同时报它的这个盲区**。

**⚠️ 与准则 13 / 20 的分界**：
- **13**（准入 ≠ 清理）讲「**某个守卫**只收不吐 ⇒ **它管的那一类**对象单调累积」——
  ⚠ 那是**一个守卫内部**的失衡；
- **20**（被默认值挡着的隐患）讲「**某条路径**为什么至今没出事」——
  ⚠ 那是**一条具体路径**的存在性；
- **本条**讲「**所有守卫都正常，而整体产出全部流向机制自身**」—— ⚠ 那是**系统的层**，
  ⚠ 且**它不可能被任何单条守卫发现**（因为每条守卫的判据都是局部的）。

⚠ **共性**：它们都在治「**只看局部就以为掌握了整体**」，
⚠ 而**本条最贵**：13 / 20 的代价是**一类对象**或**一条路径**，
**本条的代价是【整个系统的产能】—— 且它在每一秒都看起来工作正常。**

## ⭐⭐ 修订（2026-09-29）：把量法从【静态计数】改成【执行期干扰】

⚠ 上面那个「最近 N 笔里有多少笔触及了系统的目的」是一个**窗口统计** ——
⭐ 它**说得对，但太迟**：⚠ 它是**事后**的，⚠ 而**代价是在做正事的过程中付掉的** ✓

⭐⭐ **执行期判据（⚠ 当场可判，⛔ 不必等一个窗口）**：

```
① 开工前：声明这次要交付的【非机制产物】是什么。
② 执行中：凡【不改变该产物】且【不解除明确阻塞】的动作 ⇒ 计为一次【机制动作】。
③ 通过条件：机制动作数 = 0。
```

⚠ **若机制动作数 > 0** ⇒ ⭐ 那**就是一次执行期干扰** ⇒ **只有两个正当出口**：
**停下来，或把这次任务重新声明为机制任务**（⚠ ⛔ 不许「顺手做一下」）。

⭐ 一句话：**做正事的时候，任何不推进那件事的动作，都是机制在借用这次执行。**

⚠ **记账单位因此换了**：
- ⚠ 旧：**机制类产出占比**（⚠ 它自己会趋近 100%，而你**每一天都看起来在推进**）
- ⭐ 新：**一次非机制任务里，机制动作数 / 返工轮数**（⚠ **它当场就是 0 或不是 0**）✓

## ⭐⭐ 修订（2026-10-01）：机制吃产能的**定价机制** —— 「复核便宜，关闭贵」

判据：**「在这套机制里，【正确的动作】与【替代它的、成本更低的动作】，各要付什么？」**
⚠ **若后者更便宜、而前者还额外要承担风险 ⇒ agent 会系统性地只做后者** ✓

**⇒ 为什么**（这是本条要补的那一半 —— 前两次修订说了「机制在吃产能」，⛔ 没说**它为什么会被选中**）：
在这套机制里，**关闭**一条要**逐条登记豁免**（⚠ 会撞上一道守卫，要人读、要引用）；
而**复核**一条**什么都不撞** ⇒ ⭐ **两者都产出「提交」，而只有前者会减少未处理项** ✓
⇒ 于是**理性地选便宜的**，正是**被这套机制激励出来的** ✓

⭐ **而比「贵」更硬的一层（2026-10-01 追加，⚠ 一手实测）**：在那套系统里，**降低「未处理项数」这个动作，是被【明文规矩】挡住的** ——
规则逐字是「**首标记是条目【自己的声明】—— 不许靠改它去改计数**」。
⇒ ⭐ **于是「关闭一条」不是「贵」，而是【默认不被允许】** ✓
⚠ 而那条规矩**本身是对的**（它拦的正是「为了让数字好看而误关」）⇒ ⭐ **但它的代价是：那个计数【天然不会快速下降】**，
⭐ 所以**在一个给定窗口里看到「净 0」，既不证明偷懒、也不证明机制坏了** ——
⚠ **它可能只是【那个数字在设计上就不接受清理】** ✓
⇒ ⭐⭐ **正确的做法不是去降它，而是**：① 把**真的可动的**做掉 ② 把**不可动的**（等外部的人 / 等外部条件 / 周期不可闭 / 被明文留住）**移出主列表** ✓

⚠ **⚠ 而它极难被发现，因为【两个动作看起来都在工作】**：
每一笔提交都真实、都有措辞、都能通过检查，⭐ 只是**它们没有改变任何状态**。

**实例（单人-单机自动化系统，2026-10-01 实测）**：⭐ 量一个 **3.6 小时 / 51 笔提交** 的窗口：

| 类别 | 笔数 | 占比 |
|---|---|---|
| 机制/记录（跨轮锚点 · 快照 · 设计文档 · 记忆 · 技能） | 20 | 39% |
| 任务·**只读复核**（复核 / 复算 / 订正措辞，**不改变状态**） | 15 | 29% |
| 任务·动手（实现 / 立项 / 登记进队列） | 10 | 20% |
| 未归类 | 6 | 12% |

⭐ **而「动手」那 10 笔里，真的把未处理项数减下去的只有 2 笔** ⇒
⭐⭐ **3.6 小时的净结果 = 减少 2 · 新增 2 = 净 0** ✓

⭐ **并附一条同源的**：那个「未处理项总数」本身是**复合指标** —— 它混了
真待办 / 等外部的人 / 等外部条件 / **周期永不可闭** / **已完成未关** / 无复核痕
⇒ ⚠ **把它当 KPI 去优化，会产生反向激励**（⭐ 例如为了降数而**误关**）✓
⇒ ⭐ **正确做法：先按「能不能动」分桶，⭐ 主看【可动的那一桶】，⛔ 不是总数** ✓
