# Turning "criticism and lessons" into mechanisms — a portable set of practices

> **Source**: one user, collaborating with an AI agent over a long period, saw the same kinds
> of mistakes recur. He rejected "I'll be careful next time" as a solution, and demanded that
> **every lesson be turned into something that "runs every time"**. This document is the
> abstracted version of that practice (**contains no specific project / business / data
> information**).
>
> **Core proposition**:
> > **A lesson written in a document = not written. Any line of defence that relies on "being
> > conscientious" is no line of defence at all.**
> > The definition of a mechanism is: **it still takes effect at the times when you have
> > forgotten about it.**

---

## 0. First, define the threshold for "mechanism": four gates

Before building any mechanism, accept this criterion first — it comes from a real measurement:

> **Between "built" and "takes effect" stand four gates:**
> **① it is called  ② it finishes within budget  ③ it actually appears in the output that is
> consumed  ④ someone will read it**
>
> **If any gate is not passed, the mechanism does not exist — and it still gives people the
> illusion that they "already have it".**

**Two real counterexamples** (both genuine):
- After a **rule document** was built, a repository-wide `grep` for references returned **0**
  ⇒ the next session simply does not know it exists.
- A **check** was wired into a startup hook, but **the hook has a 20-second timeout**, and one
  query inside that check takes **19.5 seconds** ⇒ **the whole block of checks after it was
  never executed**, and the hook's exit code was 0 ⇒ **nobody knew.**

**⇒ Acceptance criterion (one line)**:
> **For every mechanism, ask: "If it dies / it doesn't run / it gets cut off, who knows?"**
> **If you cannot answer, gates three and four are not passed.**

## 1. Mechanism one: put the code of conduct into a channel "injected at every session"

**Problem**: writing a lesson into a document ⇒ it takes effect only when someone **actively
goes and reads that file** ⇒ and people (and agents) do not actively read when they are rushing
a task.

**The practice**:
```
① Each rule = one small standalone file, with a uniform filename prefix (e.g. `guideline-*.md`),
   and an extremely short body: one criterion + one real instance.
② Write a script that **automatically derives** a one-page checklist from these files and
   outputs it to the channel that gets injected at session start.
③ ⚠ **Never hand-copy**: the checklist must be generated by the script from the rule files.
   — A hand-copied duplicate will inevitably drift, and drift silently (measured: in one
     hand-copied rule checklist, the item count, the item contents, and the item numbering
     were all wrong, and nobody noticed).
```

**The criterion**: **Any "N items of X" checklist must either be the source of truth itself, or
a reference with a checker attached — one of the two.**

**Why "automatic derivation" rather than "building a new entry point"**:
a newly built entry point is itself a gate-four risk (nobody will go and use the entry point
you just built). **Hooking into an existing channel that is certain to run** (session start /
pre-commit hook / scheduled task) is the reliable path.

**⚠ And this channel has a **very narrow interface** -- write it down, or you will keep stepping on it:**

**The derived listing takes only the opening `判据：` line of each file (plus its continuation
lines). Body paragraphs do NOT enter the channel.**

**Measured cost (2026-09-21)**: I added a **behavioural rule** ("a guard whose entry condition does
not hold must also go red") to the **body** of a guideline file, and then announced it had "landed
in the mechanism".
**=> It landed in the document, not in the injection channel -- the agent inside a session cannot
see it.** And **a behavioural rule is precisely what this channel exists for.**

**=> Criterion (three layers, each narrower)**:
> **Written in a local docstring = not written** (only whoever reads that file sees it).
> **Written in the body = only whoever reads the document sees it.**
> **Written into the `判据：` line = the session sees it too.**

**=> So that line is not a "summary" -- it is the single injection interface.
Anything you want the agent in a session to remember has to land on it;
the body is for the human reading the document. The two are layers, not duplication.**

## 2. Mechanism two: a dictionary of error types — three things for each type

**Problem**: "be careful next time" is not executable. What is needed is a **detectable
signature** (when should I recall this rule) and a **triggering action** (what should I do).

**Format** (a fixed set of three for each type):
```markdown
# Type N · <one-line name>

**Typical instance**: <one that actually happened, including the wrong conclusion at the time and the truth>

**Detectable signature**:
    <What state am I in when this class of risk is highest? Use the form "I am about to do X ⇒ have I checked Y?">

**Triggering action**:
    <Concrete enough to execute, not a principle>
```

**Two design points**:
1. **The "detectable signature" must be written as "the situation I am in right now", not "an
   abstract quality".**
   - ✗ "Be rigorous"
   - ✓ "I am about to report 'this is a defect' ⇒ have I checked whether its comments say
     'this is by design'?"
2. **The "triggering action" must be an action** (which script to run / which sentence to write /
   which step to do first), not an attitude.

**⚠️ Do not add new categories casually**: in real measurements, **merging a new lesson into an
existing category** (as an "instance" or a "subtype") was more effective than opening a new
category — because the longer the checklist, the lower the probability that it gets read.
**The criterion**: **"Would its existence spawn other categories?" Yes ⇒ only then does it
deserve a new entry at the front; otherwise append.**

## 3. Mechanism three: a checklist reconciliation hook (to treat "missing answers")

**Problem**: the user listed 14 items in one message; the agent answered 12 and wrapped up.
**It itself believed it had finished.** This is **output truncation**: it stops when it "feels
it has answered enough", **without checking whether it answered everything**.

**The practice**:
```
A hook triggered "when the user submits a message":
  ① **Extract the numbered items** from the message ("1. … 2. … 3. …" or "N places")
  ② If the item count ≥ a threshold ⇒ **automatically remind**: "this message contains N
     numbered items; reconcile item by item when replying"
  ③ Otherwise **exit silently** (do not interrupt — otherwise it becomes a noise source itself)
```

**Why it must be a hook, not an "on-demand script"**:
> **"On demand" = relying on conscientiousness**: if you remember to run it ⇒ it runs; if you
> forget ⇒ it doesn't; if you don't know about it ⇒ it doesn't.
> **And that is precisely the problem being solved.**

**The accompanying criterion**: **"I have done X" ≠ "I have answered Y". First count how many
questions the other party asked, then count how many you answered.**

## 4. Mechanism four: a dispatch template (for tasks delegated to subagents)

**Problem**: the same omission recurred across rounds of delegation, **because the brief was
improvised each time**.

**The practice**: make the brief a **fixed set of phrasings**, each corresponding to a real
injury:

```markdown
## Three questions to ask yourself before dispatching
1. Is this work already done? (Check version history first; do not trust the task list's status column)
2. For the "known-bad input", have I written clearly **how to obtain it**? (see below)
3. When were the line numbers / figures I gave read? (line numbers must come with "when they were read")

## Must be written into the brief, item by item
- **Verify the actual state first** (version history); if you find it is already done ⇒ stop
  immediately and report; **do not redo it according to the brief**
- **How to obtain the known-bad input**: get the "known-bad version" by `fetching a historical
  version to a temporary path`;
  **never modify any tracked file in place** (otherwise one command timeout turns "proof" into
  "contamination")
- Commit in the form that **commits only specified paths**; verify the staging area before committing
- **Assertions must clamp both ways**; one-sided is not allowed
- **Any negative conclusion of "zero hits / does not exist"** must be re-verified through a path
  without `head`
- **Unverified must be written as "unverified"**; "cannot determine" must not be written as a conclusion
- **Where you think a judgment I gave is wrong — say so directly**, with your own measurement
```

**⚠️ The most expensive one is "how to obtain the known-bad input"**:
a brief that said only "you must feed it a known-bad version to prove it fails", **without
saying "how to obtain it"** ⇒ the subagent manufactured the bad version by modifying a
production file in place, **the command timed out and was moved to the background** ⇒ **the
restore step never ran** ⇒ the working tree was left **in the broken state**, with no
indication whatsoever.
> **⇒ When you require an action, you must also give the permitted way to implement it** —
> otherwise the other party will use the most direct (and most dangerous) one.

## 4.5 Mechanism four-and-a-half: **when to use subagents / teams, and when never to**

> This is **the one most easily abused**. In one measured run the main agent dispatched 7+
> subagents, **the same class of omission recurred**, and the most expensive instance (the
> "modify the production file in place" one in §4) **was itself a product of dispatch**.
> So what follows is not "dispatching more will be more stable", but **criteria and
> counterexamples**.

### 4.5.1 First separate five things; they are often conflated into "should we parallelize"

| Means | When to use it | One-line criterion |
|---|---|---|
| **Independent review** | The conclusion will be used as a **decision input**, and the producer is myself | **Have a party that "cannot see my reasoning process, only the final artifact" check it** |
| **Parallel subagents** | The task can be cut into slices that **do not share state** | **If every subtask were done as well as possible, would they touch the same file?** Yes ⇒ it cannot be cut directly |
| **Independent worktree** | Need to isolate git write operations | **What is the worst ref / index it could modify?** If that is the current HEAD ⇒ a worktree is mandatory |
| **Background execution** | The task is long, and **I do not need to see the intermediate process** | If a human judgment is needed midway ⇒ backgrounding is instead harmful |
| **Long-lived multi-agent collaboration** | The task **spans days** and needs division of labour | Ask first: **which "hot files" do they share? Who uniquely owns each?** |

### 4.5.2 ⛔ **When never to use it** (real counterexamples)

**① When the output must "not reveal its source"** (de-identified drafts / external publications / external feedback)
- For a subagent to **abstract**, it must **first see the original** ⇒ **creating an extra leak
  surface out of nowhere**.
- Measured: an incident in which "identity information was written into a commit message" was
  precisely a product of this kind of flow.
- **⇒ Do this kind of work in the main agent**; hand the review to a party that "only sees the
  final artifact" (see 4.5.3).

**② When you cannot verify "whether the abstraction is still accurate"**
- That requires **checking against the original**, and the original **is exactly what is being
  isolated**. A subagent cannot do it.

**③ When it adds a layer of "restatement" out of nowhere**
- Every delegation = one information transfer. **And "unverified assertions" enter mainly
  through restatement** (measured, ≥4 times in a single day in the same shape: restating a
  number given elsewhere, restating a root cause given elsewhere, copying the previous round's
  conclusion into the single ledger, passing a wrong root cause to the next agent).
- **⇒ The longer the restatement chain, the more errors of this kind.**

### 4.5.3 ✅ **When it is most worth using: independent review with asymmetric context**

> **Let the reviewer see only the final artifact, not the source or the reasoning process —
> what it can see is **less than** what I can see, and that is why it can find **what I cannot
> see**.**
> (I cannot see it precisely because I know the original.)

```
Give the reviewer: the **final artifact** (document / code / conclusion) + **one specific question**
Do not give it : the raw materials, my reasoning process, my conclusions
```
**What to ask** (ask only what can be answered):
- "Is there anything in here that could point to **a specific organization / individual /
  project**?"
- "Does it read as a **standalone document**? Are there sentences that hold only if you have
  read the original?"
- "**Under what input would this conclusion fail to hold?**" (= the "a criterion can be
  vacuously satisfied" of §8)

**⚠️ A reviewer saying "no problem" ≠ it checked** — **require it to give the method, what it
saw, and how it concluded "no problem".**

### 4.5.4 Real injuries from concurrent interlocking (**ordered by harm**)

| # | Shape | Measured frequency | Mitigation |
|---|---|---|---|
| 1 | **Staging areas sweep up each other's files**: A `add`s its own files then commits **without paths**, sweeping up B's already-staged files | **4 times** in one day | Use the **commit-only-specified-paths** form; **verify the staging area's file names and count** before committing |
| 2 | **Sharing one commit identity** ⇒ afterwards **attribution cannot be determined from author information** ⇒ the main agent's "no-defect confirmation" is invalidated by this | — | When dispatching, set an **explicit commit identity** for each subagent |
| 3 | **Simultaneous commits trigger hook failure** (the hook reports a repo-wide check failure; nobody knows whose change it is) | **7+ times** in one day | The hook message must **say "whose change is failing"**, otherwise everyone who sees it goes and re-investigates a problem that is not theirs |
| 4 | **Shared "hot files" modified concurrently** | — | **List hot files first, designate a single owner**; write into the brief "if you need to change someone else's hot file ⇒ **stop and report**" |
| 5 | **"Partitioning by directory" is fake isolation** | — | Criterion in 4.5.1, second row |

### 4.5.5 ⚠️ **Subagents repeat the main agent's mistakes**

- Measured: on the same day, **two different subagents each committed a "one-sided assertion"**
  (the §8 one), and **another committed "modifying a production file in place"** (the §4 one).
- **⇒ The reason is simple: subagents do not know the lessons you learned today.**
- **⇒ So the §4 dispatch template is not "optional politeness", it is **the only** channel that
  carries the lessons to the next subagent** (unless you have already put the lessons into a
  channel auto-injected at every startup — see §1).

### 4.5.6 The main agent's **acceptance obligation** for subagent output

> **Do not take commit messages (or any self-report) at face value.**

Two measured examples:
- One agent reported "the file I broke has been restored". **Independently verified with a
  content hash that both sides matched**, and only then confirmed as true.
- Another reported "the threshold has been locked". On checking, **the constant is correct, but
  no mechanism ensures it is not changed** — **"locked" was an empty claim at the time.**

**The criterion**: **For any "verified / fixed / completed", the main agent must be able to say
"by what method I independently checked it". If it cannot say that ⇒ it is only a restatement.**

### 4.5.7 One line

> **Dispatching a subagent is not "an extra pair of hands", it is "an extra information-transfer
> hop + an extra concurrent writer".**
> **The criterion: "Who will discover this mistake?"**
> **— If the answer can only be "me myself" ⇒ dispatch a reviewer that "cannot see my reasoning
> process";
>    if the answer requires "seeing the original" ⇒ do not dispatch (that is the leak surface).**

## 5. Mechanism five: turning a "falsifiable prediction" into something with an expiry date

**Problem**: the agent gave a good mechanistic explanation with a prediction attached, **but
once the check date passes, the prediction can never be checked again**.

**The practice (three together)**:
```
① Write it into a persisted file, **including the check date** and **the check method**
   (which command / which query)
② Set a **one-shot scheduled reminder** (automatically recalled on the due date)
③ Put "**what it means if it does not hold**" into the reminder content
   ✗ "take a look at the result"
   ✓ "if it does not appear ⇒ the fix did not take effect ⇒ go back and investigate;
     **do not explain it away as 'no signal'**"
```

**The stronger form: when delivering a result that is "expected to fail", a decision table is mandatory**
```
| Symptom | Meaning | Action |
|---|---|---|
| everything normal | all is well | — |
| **error X** | **the fix is working normally** (the old code would have silently rewritten and reported success here) | **do not roll back** |
| error Y | upstream data not yet in place | backfill once the data arrives |
```
> **Without this table, the next person will roll back a "correct failure" as a bug.**

## 6. Mechanism six: authorization boundaries — they cannot be derived by "rule self-consistency"

**Problem**: the agent will use in-project rules ("reversible + no sensitive paths ⇒ do it
directly") to **derive** that it has the right to perform some **outward-facing or
irreversible** action (external publishing, writing production data, changing configuration).

**Measured**: this kind of derivation **was stopped twice by an external permission check** —
once a subagent, once the main agent itself. **The reason for stopping was the same**:
> "This change is persistent, and **no message from a __human__ named it**"

**⇒ The criterion in one line**:
> **"Was this said by a human, or by some agent?" — the latter is never enough.**

### 6.1 ⚠️ **Check before publishing externally: you must scan history, not just the working tree**

**Measured (hit while writing this very document)**:
the author edited the licence file in the working tree (removing an identity string that should
not have been there), **`grep` over the working tree = 0 hits**, and so considered it clean.
**But it was still there in history** — the version in the first commit is the old content:

```
first commit's <file>:3  → <old content>      ← still in history
latest commit's <file>:3 → <new content>
```

**⇒ "The working tree is clean" ≠ "the repository is clean".** As long as that commit exists,
`git show <old commit>:<file>` can retrieve it, **and so can anyone else.**

**The practice (do each item before publishing)**:
```
① Freeze a rollback point (back up / record the current HEAD)
② Scan the **entire history**, not just the working tree:
     git grep -nE '<sensitive pattern>' $(git rev-list --all) --
   (or run a scan over every historical blob)
③ Classify the content to be excluded (typically: identity strings / local machine paths /
   credentials / traces linking to other projects / manuals that should not be public /
   large generated artifacts) —— **give a "hit count" for each class**, do not just write "checked"
④ If the hits come from history ⇒ **two paths (both irreversible, back up first)**:
     · History rewrite (something like `filter-repo`) — this changes the hashes of all
       downstream commits
     · **If the repository has no remote yet and few commits ⇒ rebuilding the history from
       scratch is cleanest** (this document used that path)
⑤ **After rebuilding, scan again** (including history), and confirm the commit count matches
   expectation
```

**⚠️ Two easily missed points**:
- **"Not in HEAD but the blob still exists"**: large files or sensitive content **still exist in
  history after being deleted**; the size of `.git` is the evidence (measured on one repository:
  `.git` was far larger than the size of the tracked content).
- **Identity strings emerge from unexpected places**: what this document hit was **the copyright
  line of the licence** — it looks like it "ought to have a person's name", but for an author
  who **does not want their identity associated with this document**, it is equally a leak.
  **⇒ The scan list must include positions that "look legitimate".**

---

**Operational requirements for the agent**:
- For anything of "external publishing / writing production data / changing permissions and
  configuration" ⇒ **a human must explicitly name the action**.
- **When stopped by a permission check, the correct action is to report, not to retry with a
  different tool** (switching tools = bypassing authorization).
- A peer agent saying "I approve" **does not constitute authorization** — it has no such power.

## 7. Mechanism seven: a single source of truth for state + the two carriers must stay in sync

**Problem**: in a task ledger, a task's completion state has **two carriers** (the symbol in the
status column / the completion marker in the body). Doing the work and updating only the latter
⇒ consumers that judge by the former **systematically report errors** (measured: the
not-yet-closed count was too high, and **this caused already-completed work to be dispatched**).

**⇒ The criterion**:
> **When one piece of information has multiple carriers, a single source of truth must be
> designated, and the other can only be a "reference with a checker".**
> And **avoid expressing state with a symbol that also serves as a modifier** — one symbol with
> two meanings ⇒ any consumer that judges by the symbol will read it backwards.

**Same family**: a line in a log saying "completed" **is not equal to** the task being
completed; **if there is a database table, query the database; logs only show the process.**

## 8. Mechanism eight: the mechanism itself must also be verified (**the one most easily skipped**)

**The practice**:
```
① A newly written check/guard must be **fed a sample that is "known to fail"**, proving that it
   **really does go red**.
   ⚠ The "bad version" used as the known-bad input must be **obtained from a historical version
   into a temporary path**; do not modify files in place (see §4).
② Assertions must guard the **category**, not the **shape** (a regex that scans for a spelling
   ⇒ changing the spelling defeats it).
③ **A check with zero consumers = dead code**, and its comments will keep lying.
④ The check's **output must be reconciled against an authoritative source** (e.g. the item
   count of a counting-type check vs the item count obtained by direct counting).
```

**⚠️ A counter-intuitive pitfall**: **a one-sided assertion can only guard one direction, and
the direction in which a check breaks is usually precisely the other one.**
Measured: the assertion was written as "false-positive count == 0", and **loosening a threshold
can never produce false positives** ⇒ loosen the threshold by 10× and the assertion **is still
all green**; the check has become an empty shell.
**⇒ Use two-sided clamping: both bounds must have a basis.**

**Another one**: **"a criterion can be vacuously satisfied"** — the check's condition is
**always true** in the target scenario. Measured: **7** found in a single day, in varied shapes
(unit mismatch / insufficient coverage / finite resampling returning 0 / resolution insufficient
to reach the threshold / allowlist shape / a terminal-state marker hung on a periodic task /
paging without completeness verification).
> **⇒ The criterion: "Under what input would this criterion be false?" — if you cannot answer
> that, it may be always true.**
> **⇒ The actionable version: measure the pass rate item by item. Hard checks at ≈100% are
>   candidates (but you must read the documentation item by item — for soft checks designed to
>   "observe only, never block", 100% is by design).**

## 9. The cost and boundaries of this practice (**stated plainly**)

- **It adds short-term friction**: every dispatch / commit has to go through the checklist.
  Measured cost: in one day, the documentation-consistency hook **blocked commits 7+ times**,
  each requiring running a fix script and an extra commit.
- **Its benefit is asymmetric**: most of the time it is just "going through it once more", but
  **occasionally what it blocks is the kind that "would make the conclusion wrong" or that is
  "irreversible"** — one such time pays for the cost.
- **It does not solve "not knowing"**: it only solves "knowing but not doing". A mechanism
  cannot discover for you the directions you did not think of.
- **It gets masked by its own success**: when the mechanisms are all working, **you cannot see
  what it blocked** (because it did not happen). ⇒ **Do not delete them just because "nothing
  has gone wrong recently".**
- **It must self-maintain as the source of truth drifts**: thresholds, counts, and paths all
  change. ⇒ Every "number that can change" must be **derived by a script from the source of
  truth**, paired with a check that **blocks commits when it drifts**.
