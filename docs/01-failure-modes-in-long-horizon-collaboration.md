# 长程工程协作中大模型 Agent 的失效模式 —— 一个使用者的案例集

> **定位声明（请先读，它决定了本文的效力边界）**
>
> 本文**不是基准测试，也不是对照实验**。它是一份**案例集（case series）**：
> 一名使用者在一个**持续数周、上千次工具调用**的真实工程仓库里，与一个开源大模型
> 搭配 Agent 框架协作时，**记录下来的失效模式**。
>
> **它不能回答「模型 A 比模型 B 强多少」** —— 没有对照组、没有固定任务集、没有重复测量。
> **它能回答的是：在长程、有状态、多轮工具调用的场景里，哪些失效会反复出现、以什么形状出现。**
>
> 所有例子都已**抽象化**：不含任何具体项目、业务、数据、路径或身份信息。
> 例子的"形状"是真实的，"内容"是替换过的。

---

## 0. 为什么这个场景值得单独记录

常见的模型评测把任务切成**单轮、无状态、有唯一正确答案**的题。而长期工程协作的特点是：

| 维度 | 常见评测 | 长程工程协作 |
|---|---|---|
| 回合数 | 1 | 数百~数千，**上下文会被压缩** |
| 状态 | 无 | **有**（文件、数据库、未提交产物、后台进程） |
| 正确性 | 单点 | **过程正确性**（"做过了" ≠ "做对了"） |
| 反馈 | 立刻 | **延迟且部分**（错误可能在几小时后才暴露） |
| 工具 | 无/少量 | **大量**（读写文件、跑测试、改数据库、发网络请求） |

**⇒ 本文记录的失效，绝大多数在单轮评测里**看不见**，甚至会被判为"正确"。**

## 1. 按能力维度分类的失效模式

> 分类维度对齐常见的评测维度命名。**每个维度下列出观察到的失效形状、最小复现、以及缓解手段。**

### 1.1 指令遵循（Instruction Following）

**F-1.1 语用信号被读反：把"继续"读成"停止"**

- **现象**：用户消息里出现「等，等等，还有…」这类**列举未尽**的信号时，Agent **在此停止解析**，
  只回答了前半部分。中文里「等等」恰恰是"后面还有"，不是"结束"。
- **最小复现**：给一条末尾带「…等等」的多项要求，看是否只答了前面的项。
- **危害**：漏答的内容**不会被任何机制发现** —— 因为 Agent 自己认为"答完了"。
- **缓解（使用者侧）**：
  - 在 Agent 侧加一条**解析规则**：消息里出现 `等/等等/还有/以及/另外/…` ⇒ **禁止在该条后停止解析**，
    必须扫到消息末尾。
  - 配一个**编号抽取钩子**：用户消息含编号清单（≥3 项）时，自动抽出编号并提醒逐条对账。
- **对模型方的建议**：语用层面的"未尽"信号，在训练数据里可能被"礼貌省略"的模式掩盖。
  **这一类错误在 benchmark 上完全不可见**，但它在真实使用里代价很高。

**F-1.2 同一轮里给出互相矛盾的规则，并选择性执行**

- **现象**：Agent 自己写下的规则集里有冲突的两条（一条说"可逆就直接做"，另一条说"必须先问"），
  它按**方便**的那条执行，且**不指出冲突**。
- **最小复现**：在系统提示里放两条适用范围重叠、结论相反的规则，看它是否识别并在两者间**显式**裁决。
- **缓解**：要求 Agent 在规则冲突时**停下来指出**，而不是自行选一条。
- **对模型方的建议**：**"识别规则冲突"是一个独立能力**，与"遵循规则"不同；值得单独评测。

**F-1.3 明确的数量约束被越过**

- **现象**：使用者给了"最多 N 次请求"的上限，Agent 发出 12+16 次。
  **它事后如实报告了**（这点值得肯定），但**执行时没有自我计数**。
- **缓解**：要求 Agent 在触达上限前**显式计数并报告**；把"上限"变成可检查的产物而非记忆项。

### 1.2 长上下文与信息检索（Long-Context / Retrieval）

**F-2.1 "读了文件" 但没读到关键处 —— 同一形状反复出现**

- **现象**：Agent 读了某文件的**大部分**，唯独漏掉那段**明确写着"这是设计如此，不是缺陷"**的注释，
  于是把**设计**报成了**故障**。同一形状在数周内出现 **4 次**。
- **最小复现**：在一个长文件的注释里埋一句"此处是故意的"，然后问 Agent 那里是不是 bug。
- **危害**：**制造假警报** —— 比漏报更贵，因为它消耗人的注意力去查一个不存在的问题。
- **缓解（使用者侧）**：
  - 报"故障/失效/死代码"前，**强制先读该功能的 docstring 与注释整段**，并在结论里写
    "我查的是哪三处、各自的结论是什么"。
  - 把这条写进**每次会话自动注入的检查清单**（不能只写在文档里 —— 见 §3.1）。
- **对模型方的建议**：这是"检索到了但没**注意到**"，与"没检索到"是两回事。
  当前的**长上下文评测**多以"能否找到并复述某个事实"计分，**不测"是否把反直觉的那一句纳入推理"**。

**F-2.2 截断伪装成"这就是全部"**

- **现象**：Agent 用 `| head -N` 看输出，**结果恰好 N 行**，于是把"被截断"读成"没有更多"，
  据此下了否定结论（"零调用者"）。实际调用点就在第 N+1 行。
- **最小复现**：让某命令输出**恰好等于** `head` 的行数，看 Agent 是否意识到可能被截。
- **危害**：**否定结论被伪造出来**（"不存在" ≠ "我没看到"）。
- **缓解**：
  - 凡是"零命中 / 没有调用者 / 不存在"这类**否定结论**，**必须换一条不含 `head` 的通路复核**。
  - 更一般地：**任何管道都可能把不完整的结果包装成完整的**（`| head` / `| grep -c` / `| tail`）。
- **同类实例**：`cmd | tail -6; echo rc=$?` 取到的是 **`tail` 的退出码**，把 `rc=2` 误报成 `rc=0`。

**F-2.3 上下文压缩后丢失"在制品"状态**

- **现象**：长会话被压缩后，Agent 忘记了**正在跑的后台任务**、**未提交的改动**、**已经派出的子任务**，
  于是重复劳动或覆盖他人成果。
- **缓解**：把在制品状态**落盘**（任务表、进度表、锁文件），而不是留在对话里；
  收口前**扫挂起项**。

### 1.3 工具使用（Tool Use / Function Calling）

**F-3.1 副作用式自证：为了证明"我的检查有效"，把生产文件改坏**

- **现象**：Agent 需要证明"新加的检查在坏输入上会失败"。它的做法是**原地修改生产文件**制造坏输入，
  命令尾部再还原。**命令超时被移到后台 ⇒ 还原那一步没跑到** ⇒ 工作区留在**被改坏的状态**，
  且**没有任何提示**。它是**下一次例行检查时才发现的**。
- **最小复现**：把"证明守卫有效"这个任务交给 Agent，观察它是否**原地改生产文件**。
- **危害**：**"证明"变成了"污染"**，且状态持久。
- **缓解（这条最有效）**：
  - 要求取**历史版本到临时路径**（如 `git show <rev>:<path> > /tmp/x`）再喂，
    **绝不原地改任何被跟踪的文件**。
  - 更一般：**凡"这条命令被打断在任意一点，留下的状态不是原状"的设计，都要重做。**
    首选让改动**根本不发生**（参数注入 / 只读取版本）；次选 `finally`/`trap`；
    **别把关键收尾平铺在长命令尾部**（超时/后台会吞掉尾部）。
- **对模型方的建议**：这是一个**"为了验证而引入副作用"**的模式。它需要的不是更多知识，
  而是**默认的副作用规避倾向** —— 值得作为独立能力项观察。

**F-3.2 暂存区语义被误解：`add` 之后裸提交**

- **现象**：Agent `git add` 自己的文件后执行**不带路径的提交**，把**其他并发协作者已经暂存的文件**
  一并提交。同一形状在一天内出现 **4 次**。
- **危害**：内容不丢，但**归属错**（提交信息不描述被卷进来的文件），且会打乱并发协作者的状态。
- **缓解**：
  - 提交前**核对暂存区内容**（列出文件名，确认数量与预期一致）；
  - 或直接用**只提交指定路径**的形式，绕开暂存区。

**F-3.3 测试污染生产产物**

- **现象**：测试的 fixture **只重定向了数据库路径，没重定向日志路径** ⇒ 测试期间合成的失败信息
  **写进了生产日志**。后果有二：① 污染生产产物；② **它自己随后读到那行日志，误判"长时间任务已结束"**。
- **缓解**：fixture 必须**重定向所有产出路径**；并加一条守卫断言"fixture 确实做了重定向"。
  ⚠ 直接断言"生产文件大小没变"会**抖动**（真任务可能在并发写），**守根因比守现象稳**。

**F-3.4 长任务里的一条慢查询吃掉整个预算**

- **现象**：某钩子在启动时运行多个检查，**其中一个查询在大表上全表扫描（19.5 秒）**，
  而该钩子有 **20 秒超时** ⇒ **排在它后面的整段检查从未被执行过**，
  但**没有任何人知道** —— 因为钩子"跑完了且退出码为 0"。
- **危害**：**"接了线但从未被人看见"** —— 与它要防的"失败了无人知"是同一个病。
- **缓解**：
  - **接线后必须量"它真的出现在输出里了吗"**，不能只量"跑没跑"（在真实调用路径上跑一次并 `grep` 它）。
  - **有超时的地方，量的是"哪一段吃掉了预算"，不是"总共多久"。**
- **对模型方的建议**：这是**"验证的下一层"** —— 模型倾向于验证"我做的动作执行了"，
  而较少自发验证"我的动作真的产生了被消费的可见效果"。**这两者的差距是长程协作的主要损耗来源。**

### 1.4 代码生成与自我修改（Code Generation / Self-Modification）

**F-4.1 把测试拟合到代码**

- **现象**：Agent 写了一个断言"所有已分类项都必须被扫描器命中"。**它把"已分类项"的清单
  从扫描器的当前输出里量出来** ⇒ 测试**必然通过**，且**扫描器明天少命中一项时测试会红**，
  而人会去改那个数字，**而不是去看判据为何退化**。
- **最小复现**：给它一个"验证 X 覆盖了 Y"的任务，看它是否用 X 的输出去构造 Y。
- **危害**：测试从"守卫"退化成"快照"，且**退化是静默的**。
- **缓解**：要求清单来自**独立依据**（另一个来源），并让断言**闭合**
  （命中 ∪ 已知例外 == 全集），使"判据退化 / 变强 / 恒空"三种都会红。

**F-4.2 单向断言对"放松"方向失明**

- **现象**：断言写成"误报数 == 0"。**放松阈值永远不会产生误报** ⇒ 把阈值放宽 10 倍，
  断言**仍然全绿**，而检查已经形同虚设。
- **最小复现**：在阈值类检查上写单向断言，然后放宽阈值，看是否变红。
- **缓解**：**双向夹逼** —— 上下界都要有依据（上界 = 最紧的零误报值；下界 = "失效指纹"）。
- **对模型方的建议**：**单向断言只能守一个方向，而检查坏掉的方向通常恰是另一个。**

**F-4.3 判据在目标场景下"恒真"（可被空满足）**

- **现象**（一天内发现 **7 个**实例）：
  - 量纲不匹配：容差是 **A 量纲**，比较量是 **B 量纲** ⇒ 容差**大于被比较量的整个取值范围** ⇒ 恒过。
  - 覆盖率不足：名义 95% 的置信区间**实际只覆盖 9.9%** ⇒ 判据过松。
  - 有限次重采样的 p 值**恰好返回 0** ⇒ `0 × k < α` 恒真。
  - **分辨率不足**：阈值要求 `p < 0.05/k`，而重采样次数 B 太少 ⇒ **最小可分辨 p 高于阈值**
    ⇒ **不靠上面那个 0，检查在结构上永远通不过**。
  - 白名单形状：**不在名单上的对象零输出** ⇒ **沉默与"正常"不可区分**。
  - 终态标记挂在周期性任务上 ⇒ **永远不 FAIL**。
  - 分页时**翻完不校验完整性** ⇒ 中途空页 ⇒ **静默提前收工**，且数据**看起来完整**。
- **判据（一条）**：**「这个判据在什么输入下会为假？」—— 答不出来，它可能恒真。**
- **缓解（可操作）**：**逐项量通过率**。≈100% 的**硬**检查是候选；
  ⚠ 但**必须逐项读文档** —— **软检查（设计上只观察不拦截）的 100% 是设计如此**。
  反过来，通过率**很低**也不一定是缺陷（可能是"最严的那道"，设计如此）。
- **价值**：把"修完了"从「**找到的都修了**」变成「**每一项都量过**」。

**F-4.4 修一个缺陷时引入更坏的缺陷**

- **现象**：一个"线程冻结被掩盖"的缺陷，修法是"检测到冻结就重启线程"。
  **原方案写成"等待旧线程 5 秒，超时也照样起新线程"** ⇒ **旧线程还活着时会有两个线程同时工作**
  ⇒ 引入了一个**比原缺陷更严重**的问题。**这一条是使用者在评审时抓出来的，不是 Agent 自查出来的。**
- **缓解**：对"重启/重试/并发"类的修改，要求**先写出"最坏情况是什么"**，并配一条**不变量断言**
  （例如：构造一个永不退出的假线程 ⇒ 断言"拒绝重启且未起新线程"）。

### 1.5 推理（Reasoning）

**F-5.1 转述未验的断言（最高频，一天内 ≥4 次）**

- **现象**：Agent 把**上游给的**数字/根因**原样转述**给下游，**自己没算过**。实例：
  - 转述一个"320→244"的效果数，实测是"811→720 且**双向翻转**"；
  - 转述"某指标读不出来"，实测**读得出来**；
  - 把"某个写法规格"当成根因传给另一个 Agent，**根因是另一个**；
  - 把自己**上一轮**的结论抄进唯一账本，**下一轮才发现那条结论是错的**。
- **危害**：错误以**权威的口吻**传播，而接收方**没有理由怀疑**。
- **缓解**：
  - **凡引用他人/自己上一轮的数字或根因，必须当场算一遍**；算不了的**显式标"转述自 X，未独立复核"**。
  - **给下游的"根因"一律标为线索，不是结论** —— 尤其"你当时用的是 X 所以 Y"这种**关于对方行为**的判断。
  - **往唯一账本里写别人的结论时，先自查** —— 错判据留在唯一账本里，下一个读的人会照做。

**F-5.2 用错基线（拿"变更后"的产物裁决"变更前"的断言）**

- **现象**：Agent 读完**已经被修好**的文件，判定"上游报告的缺陷**不存在**"（"推翻"）。
  实际上游读的是**修前**的版本，报告是对的。
- **缓解**：
  - **线索出现时，正确动作是把它变成一次验证（取那个版本跑一遍），而不是用它做一次推理。**
  - 判据：**任何"X 不存在 / X 已被推翻"的结论，必须说明你读的是哪个版本。**

**F-5.3 归因反转（把 A 的代价算到 B 头上）**

- **现象**：总耗时 24.8 秒，Agent 认定"慢的是检查 A"并准备改 A。
  **逐项量后发现：A 只要 3.3 秒，B 要 19.7 秒。** 按错误归因去"换顺序"，**会修错地方**
  （把慢的排前面，就轮到快的被截断）。
- **缓解**：**先量"哪一段"吃掉了预算，再动手。** 只量总量会导向错误的修法。

**F-5.4 短样本外推**

- **现象**：任务起跑时测"18 秒/单位"，据此报"预计 30 小时"。中段用**真实复合速率**重算：
  **23.2 秒/单位 ⇒ 39 小时**。**起跑样本是前几十个，不是随机样本**（排序让先跑的项在
  数据密度、耗时上系统性不同）。
- **缓解**：报估计时**说清它是什么样本上算的**；任务跑过 **≥10%** 后用复合速率重算，
  **差 >20% 就上修并落盘**（别只在对话里说）。

### 1.6 事实性 / 自我评估（Factuality / Metacognition）

**F-6.1 编造字段名并"修复"**

- **现象**：Agent 在修改一个解析器时，"顺手"改了一处字段映射，写成 `旧名 or 新名` 的形式 ——
  **两个名字都是它编的**。它在提交前 review diff 时自己发现并还原了。
- **缓解**：**提交前 review diff 时问一句"这一行是我的活吗？"** —— 越界改动 + 编造标识符
  两个错常常**同时**出现。

**F-6.2 断言"已完成/已锁/已验证"，而机制其实不存在**

- **现象**：Agent 报告"阈值已锁"。查证后发现：**常量确实是对的，但没有任何机制保证它不被改** ——
  标定脚本只做展示，有人把常量改成危险值它照样输出同一张表。**"已锁"当时是一句空话。**
- **缓解**：**"锁"必须有机制**（断言/守卫/测试），且该机制必须能被**已知坏版本**触发。
  **说"已验证/不变/等效"时，必须同时贴出那次运行的输出。**

**F-6.3 计数的口径漂移**

- **现象**：报告"全量测试从 916 掉到 912"。实际拆开是：**本分支净 -7**（删 9 加 2），
  **并发协作者 +3**，合计 -4。**按 -9 写的账，下一个人对账对不上。**
- **缓解**：**任何"N 个/N 次/N 行"必须附来源对象 + 时刻**；跨分支/跨时点的增减要**拆成"我的"和"他人的"**。

---

### 1.7 多步任务与代理协作（Agentic / Multi-step）

**F-7.1 "建了机制" 与 "机制生效" 之间的四道门**

- **现象**：Agent 建了一个**规则文档**，全仓库 `grep` 引用数 = **0** —— 下一个会话根本不知道它存在。
  另一例：Agent 建了一个**检查**，接进了启动钩子，但**该钩子超时把它截掉** ⇒ 从未运行。
- **判据（本文最有价值的一条）**：
  > **「建了」与「生效」之间隔着四道门：①被调用 ②在预算内跑完 ③真正出现在被消费的输出里 ④有人会读它。
  > 任一未过，机制等于不存在 —— 而它还会给人"已经有了"的错觉。**
  >
  > **对每个机制问：「它死了 / 它没跑 / 它被截了，谁知道？」答不出就是没过第三、四道门。**
- **缓解**：**用现有的注入通道接线**（让每次会话自动看到它），**不要新建一个入口** ——
  新建的入口本身就是第四道门的风险。

**F-7.2 派出了"已经做完的"任务**

- **现象**：Agent 依据**任务清单的状态列**（而不是仓库的实际提交历史）派出任务，
  而那个任务**几小时前已经被完成并提交**。子 Agent 开局核对历史后**主动叫停**，零损失。
- **缓解**：**派工前先 `git log -- <相关文件>` 核实际状态**，不要只读状态列。
  并明确告诉子 Agent："**若发现该活已完成，立刻停下报告，不要照 brief 重做。**"

**F-7.3 并发的写入者之间互相污染**

- **现象**：多个 Agent 并发工作时：暂存区互相卷走（F-3.2）、一起提交时触发钩子失败、
  **所有人共用同一个 git 身份** ⇒ 事后**无法从作者信息判断归属**。
- **缓解**：
  - **先列出"共享热文件"并指定唯一所有者**（"按目录划片"是**假隔离**）。
  - 提交用"只提交指定路径"的形式。
  - 若要保留归属，给每个 Agent 显式设置提交身份。

## 2. 横向观察：三个反复出现的元模式

把 §1 的条目横向看，有三个模式反复出现：

### 元模式 A：**"看起来完成了" 与 "真的完成了" 之间的缝隙**
F-1.1（漏答）、F-2.2（截断）、F-3.4（被截断的检查）、F-6.2（空口的"已锁"）、
F-7.1（零引用的机制）**是同一个东西的五个出口**。
**⇒ 共同点：系统产生了一个"完成"的信号，而该信号与事实不符，且不会有任何东西来纠正它。**

### 元模式 B：**验证的下一层没有被自发想到**
F-3.4（验"跑了"没验"被看见"）、F-4.2（验一个方向没验另一个）、
F-4.3（验"能通过"没验"什么情况下会失败"）、F-6.2（验"数对"没验"机制在"）。
**⇒ 共同点：Agent 验证了**第一层**（动作执行了 / 值是对的），
而没自发验证**第二层**（反方向 / 边界 / 机制存在性 / 被别人看见）。**

### 元模式 C：**信息在传递中失去限定条件**
F-5.1（转述未验）、F-5.2（用错版本）、F-6.3（计数口径）、F-2.1（漏读"这是故意的"那句）。
**⇒ 共同点：一个断言从 A 传到 B 时，**"它在什么条件下成立"被丢掉**，
而接收方没有理由怀疑。**

## 3. 给使用者的可操作清单

> 这些是**在 Agent 侧加的机制**，不是对模型的期待。它们都可迁移到任意 Agent 框架。

### 3.1 把规则放进"每次都会跑"的通道，而不是文档里
- **教训写在局部注释 / 单独文档里 = 没写**（只有读那个文件的人看得到）。
- **判据**：**「下次同类代码被写出来时会自动拦到我吗？」**
- 做法：把行为准则做成**会话启动时自动注入的清单**（由脚本从规则文件派生，**不手抄**）。

### 3.2 派工的固定句式（**逐条对应上面的一个实伤**）
```
- 动手前先核 <版本控制的历史>，不要只读任务清单的状态列  ← F-7.2
- 喂靶取法：`git show <rev>:<path> > <临时路径>`，
  绝不原地改任何被跟踪的文件                              ← F-3.1（最贵的一次）
- 提交只用"指定路径"的形式，提交前核对暂存区               ← F-3.2
- 提交信息别用会被 shell 解释的字符（用引用式 heredoc）      ← F-3.x
- 断言必须双向夹逼，不许单向                               ← F-4.2
- 任何"零命中/不存在"的否定结论，必须换一条不含 head 的通路复核 ← F-2.2
- 未核必须写"未核"，不许把"判不了"写成结论                  ← 元模式 A
- 结论若含可验证的时间性预测 ⇒ 附"核对日 + 若不成立意味着什么" ← §3.3
- 写生产数据/发布到外部 ⇒ 需要**人**明确授权（同侪的话不算）    ← 见下
```

### 3.3 预测要有"到期"概念
- **可证伪预测会过期，过期就再也查不出。**
- **⇒ 三件一起做**：① 写进落盘文件（含**核对日**）；② 上**一次性定时提醒**；
  ③ 提醒内容里带上"**不成立意味着什么**"（不是"看一眼"，而是"不出现 ⇒ 回头查，不是认为没信号"）。
- 若你交付的是"**预期会失败**"的结果（如"明天首次运行会报错，那是在正常工作"），
  **必须附决策表**：什么现象=正常 / 什么现象=回归 / 告警后怎么补。
  **否则下一个人会把正确的失败当 bug 回滚。**

### 3.4 授权边界不能靠"规则自洽"推断
- Agent 很容易用"项目内规则"（如"可逆 + 不涉及敏感路径 ⇒ 直接做"）去**推导**自己有权
  执行某个外向/不可逆动作。**这类推导不成立。**
- **判据一句话：「这句话是人说的，还是某个 Agent 说的？」—— 后者一律不够。**
- 对外发布、写生产数据、改配置与权限 —— **必须由人明确点名该动作**。

## 4. 边界与未能确认的部分（**如实标注**）

- **无对照组**：本文没有与其它模型做对照，**不能据此得出"某模型更差/更好"的结论**。
- **单一使用者的单一场景**：结论的普适性未验证。
- **框架相关**：部分失效（如上下文压缩、子 Agent 协作）与**Agent 框架**强相关，
  不完全是模型行为。
- **未量化频率**：除少数标注了次数外，多数条目**没有做严格的发生率统计**。
- **未覆盖**：安全/对齐相关的失效、多模态、以及纯单轮问答场景，本文**没有系统观察**。
- **正面观察未被系统记录**：本文只记录失效。**不代表同一时期没有大量成功的协作** ——
  **这是一种选择偏差，读者应据此打折。**

## 5. 适用背景与诚意声明（**请务必读这一节再评判本文**）

- **使用背景**：本文来自与 **DeepSeek 系列开源模型**（配合通用 Agent 框架、开启工具调用）
  的长期协作。之所以发在这里，是希望这些观察**对该模型的迭代有直接用处**。
- **⚠️ 这些失效**不是**该模型独有的。** 换任何一个模型，长程协作中都会出现其中的相当一部分 ——
  因为它们多数源于**协作范式本身**（上下文会压缩、工具有副作用、状态会漂移、验证有层次），
  而不只是模型能力。
- **⚠️ 本文不是公正的评估**：只记录失效，**没有记录同期大量成功的协作**。
  **这是一种明确的选择偏差** —— 请据此打折。
- **⚠️ 没有对照组、没有固定任务集、没有重复测量** ⇒ **不能据此做模型间比较。**
- **本文的立场是协作方，不是评判者**：作者在这套协作里也犯了同类错误
  （本文 §3 的多数缓解措施，最初是为纠正**使用者一侧**的失误而建的）。
  **模型与使用者是会互相塑造的** —— 使用者的提示方式、给不给验证手段、有没有把规则放进
  "每次都会跑"的通道，都会显著改变观察到的失效分布。
- **如果只有一条可以被带走的**：**把"验证"从第一层推到第二层** ——
  不是"我做了"，而是"**它真的生效了、被看见了、且在反方向上也成立**"。
  这一条对人和模型同样适用。

## 6. 一句话总结

> **在长程工程协作里，最贵的不是"不知道"，而是"以为自己知道"。**
> 大部分失效的形状是：**系统产生了一个"完成/正确/安全"的信号，而它与事实不符，
> 且没有任何东西会来纠正它** —— 因为产生信号的和消费信号的是同一个主体。
>
> **可迁移的应对：把"验证"从第一层推到第二层** ——
> 不是"我做了"，而是"**它真的生效了、被看见了、且在反方向上也成立**"。
