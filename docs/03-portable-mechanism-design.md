# 让机制跨 Agent 生效：分层与能力检测

> **问题**：机制依赖**宿主的能力**。而各家的 Agent 能力差别极大 ——
> 有的支持会话级钩子，有的只读项目根的一个文件，**纯 API 调用则什么钩子都没有**。
> **⇒ 把机制做成单一形态，必然只对一类宿主生效。**
>
> **本文给出一套分层设计：把机制拆成 5 层，按宿主能力装上尽可能多的层，
> 并让每一层都能被独立验证。**
>
> ⚠ 沿用本仓库的立场：**没有对照组，是一套工程做法，不是基准结论。**

---

## 1. 先看清差异：宿主能力矩阵

| 宿主形态 | 会读项目根的文件？ | 支持会话钩子？ | 支持提交钩子？ | 能被外部调度？ |
|---|---|---|---|---|
| 带钩子的 CLI Agent | ✅（`AGENTS.md` / `CLAUDE.md` 之类） | ✅ | ✅ | ✅ |
| 不带钩子的 CLI Agent | ✅ | ❌ | ✅ | ✅ |
| IDE 内嵌 Agent | 部分 | ❌ | ✅ | 部分 |
| **纯 API 调用**（自己写循环） | ❌（没人替它读） | ❌ | ✅ | ✅ |
| 人工操作（你自己） | — | — | ✅ | ✅ |

**⇒ 这张表就是全部问题的来源。** 任何"接在钩子上"的机制，
**对"纯 API 调用"和"不带钩子的 CLI"的覆盖是 0** —— 而这两类占实际使用者的大多数。

---

## 2. 解法：五层，按能力递进

| 层 | 依赖 | 覆盖谁 | 强度 | 失败时 |
|---|---|---|---|---|
| **L0 文本层** | 无 | **所有**（含纯 API、人工） | **最弱**（靠模型/人自觉） | 无感 |
| **L1 项目文件层** | 宿主会读项目根的文件 | 多数 CLI Agent | 中 | 无感 |
| **L2 提交钩子层** | 项目用 git | **几乎全部**（见 §3） | **强（机器强制）** | **阻断提交** |
| **L3 会话钩子层** | 宿主支持会话级钩子 | 少数 CLI Agent | 强 | 注入提醒 |
| **L4 外部调度层** | 有定时任务 / CI | **全部** | 强（但**滞后**） | 告警 |

**核心原则：**
> **不要问"哪种形态最好"，要问"这个宿主支持到第几层"，然后装上它能到的最高层。**
> **每一层都要能独立生效** —— 缺层不等于失效。

---

## 3. ⭐ 为什么 **L2（提交钩子）是跨 Agent 的最大公约数**

- **任何 Agent 写的代码，最终都要提交。** 会话钩子、项目文件都只是"劝"，**提交钩子是说"不"**。
- **它不依赖宿主**：只依赖"这个项目是 git 仓库"。
- **它对"纯 API 调用"同样生效** ---- 因为最终提交代码的也是人或脚本，走的是同一条路。
- **代价**：它是**事后**的（跑在提交那一刻），不能阻止错误发生，只能阻止错误**进库**。
  **⇒ 但对"不可逆的污染"而言，事后阻断已经是决定性的一层。**

**⇒ 结论：把最硬的检查放在 L2。L0/L1/L3 负责"少犯"，L2 负责"不让进库"。**

**⚠️ 一条必须承认的边界**：**L2 只能管住"经过 git 的动作"。**
写生产数据库、发对外请求、改配置 —— **这些不经过 git** ⇒ **L2 管不到** ⇒
**这类"外向/不可逆"动作只能靠 L0/L1 的规则 + 人的授权**（见准则 11）。

---

## 4. 能力检测：安装器怎么选层

安装器**不假设**宿主能力，而是**探测**，然后**只装能装的**，并把结果如实报出来。

```
探测顺序（每一步都可能失败，失败就降级，绝不报错退出）：
  ① 宿主标识        从环境变量 / 已知的配置目录推断是哪家
  ② L1 的目标文件   该宿主的项目级/用户级配置文件路径是什么、存不存在
  ③ L3 的钩子能力   该宿主有没有可写入的钩子配置；**不要猜，按已知清单查**
  ④ L2 的可用性     当前目录（或给定目录）是不是 git 仓库
  ⑤ L4 的可用性     有没有可注册的定时任务（这一层**默认不装**，只提示）
```

**⇒ 输出必须是一张"装了什么 / 没装成什么 / 为什么"的表**，
而不是笼统的"安装成功"。

> **判据：「它死了 / 它没跑 / 它被截了，谁知道？」**
> 安装器**自己要回答这个问题** —— `status` 必须能说出**每一层现在是活的还是死的**。

---

## 5. 每一层怎么"自证"（**四道门的具体化**）

沿用 §0 的四道门 —— **①被调用 ②在预算内跑完 ③真正出现在被消费的输出里 ④有人会读它** ——
逐层给出可执行的验证方式：

| 层 | 怎么验「真的生效了」（不是"装了"） |
|---|---|
| **L0** | **无法机器验证** ⇒ **必须如实标注**：这一层靠自觉，工具不能替你保证。⚠ 不要假装它有效。 |
| **L1** | 在宿主的**真实读取路径**上触发一次，确认它能读到（例如开一个新会话，看它是否提及该文件）。 |
| **L2** | **故意制造一次违规提交**，确认它**真的被阻断**。⚠ **没被阻断 = 这一层不存在**。 |
| **L3** | 触发一次真实事件，**在输出里 `grep` 到那段注入** —— ⚠ 本项目实测过一个反例：接进了钩子，但**钩子超时把它整段截掉** ⇒ 从未执行过。 |
| **L4** | 看它**上一次真的跑了吗**（读它的产出，不是读调度器的"已完成"标记）。 |

**⇒ 一张通用判据**：**对每一层问「拿什么证据说它现在在生效？」——
答不出，就把它标成"未验证"，而不是标成"已安装"。**

---

## 6. 隐私：诊断包只含结构，不含内容

用户报告问题时，最容易的做法是"把你的配置文件贴上来"。**这是错的** ——
**那个文件里可能有别人的私密内容**（提示词、内部路径、项目信息）。

**⇒ 诊断包的设计规则：**
```
✅ 可以带：版本号 / 操作系统与 Python 版本 / **装了哪几层** / 目标的**路径**与**是否可写**
          / 块是否存在 / 块的**长度与哈希**（用于判断"是否与发布版一致"）
          / 每层的**自检结果**（通过/失败）
⛔ 绝不带：文件的**任何内容** / 环境变量的**值** / 用户名 / 主机名 / 项目文件清单
```
**⇒ 判据**：**如果一个字段会让第三方推断出"这个人是谁 / 在做什么项目"，它就不该进诊断包。**

---

## 7. 这一层设计的边界（**如实说**）

- **L0 本质上不可保证** —— 它靠模型或人自觉。**任何声称"装了 L0 就安全了"的说法都是假的。**
- **L2 只能管 git** —— 写数据库、发请求、改配置这些**不经过 git 的动作，它管不到**。
- **L3 的覆盖面天生很窄** —— 支持会话钩子的宿主是少数，**且各家的钩子语义不统一**。
- **能力检测会过期** —— 宿主的钩子能力是**会变**的。⇒ 检测清单要**可配置**，并在 `status` 里
  如实报出"我按哪一版清单检测的"。
- **没有对照组** —— 本文的分层是**设计**，不是"实测更有效"的结论。

---

## 8. 一句话

> **机制的可移植性，不来自"更强的机制"，来自"按宿主能力分层，并如实报告哪层没装上"。**
>
> **而最该做硬的那一层，是提交钩子 —— 因为它是唯一一层
> 「不依赖宿主、又真的能说不」的机制。**
