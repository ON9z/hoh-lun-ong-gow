# 把"批评教训"变成机制 —— 一套可迁移的做法

> **来源**：一名使用者与 AI Agent 长期协作时，反复出现同类失误。
> 他拒绝"下次注意"这种解法，要求**每一条教训都必须落成"每次都会跑"的东西**。
> 本文是这套做法的抽象版（**不含任何具体项目/业务/数据信息**）。
>
> **核心命题**：
> > **教训写在文档里 = 没写。凡是"靠自觉"的防线，等于没有防线。**
> > 机制的定义是：**它会在你不记得它的时候仍然生效。**

---

## 0. 先定义"机制"的门槛：四道门

在动手建任何机制之前，先接受这个判据 —— 它来自一次实测：

> **「建了」与「生效」之间隔着四道门：**
> **① 被调用  ② 在预算内跑完  ③ 真正出现在被消费的输出里  ④ 有人会读它**
>
> **任一未过，机制等于不存在 —— 而它还会给人"已经有了"的错觉。**

**实测的两个反例**（都是真的）：
- 一个**规则文档**建好后，全仓库 `grep` 引用数 = **0** ⇒ 下一个会话根本不知道它存在。
- 一个**检查**接进了启动钩子，但**钩子有 20 秒超时**，而该检查里有一条查询要 **19.5 秒**
  ⇒ **排在它后面的整段检查从未被执行过**，且钩子退出码为 0 ⇒ **没有人知道。**

**⇒ 验收判据（一句话）**：
> **对每个机制问：「它死了 / 它没跑 / 它被截了，谁知道？」**
> **答不出来，就是没过第三、四道门。**

---

## 1. 机制一：把行为准则放进"每次会话都会注入"的通道

**问题**：把教训写进文档 ⇒ 只有**主动去读那个文件**时才生效 ⇒ 而人（和 Agent）在赶任务时不会主动读。

**做法**：
```
① 每条准则 = 一个独立的小文件，文件名带统一前缀（如 `guideline-*.md`），
   正文极短：一句判据 + 一个真实实例。
② 写一个脚本，**从这些文件自动派生**出一页清单，输出到会话启动时会被注入的通道。
③ ⚠ **绝不手抄**：清单必须由脚本从准则文件生成。
   —— 手抄的副本必然漂移，而且漂得无声无息（实测过：一份手抄的规则清单里，
      条目数、条目内容、条目编号全错了，且没人发现）。
```

**判据**：**任何「N 条 X」的清单，要么本身是事实源，要么是带检查器的引用 —— 二者必居其一。**

**为什么用"自动派生"而不是"新建一个入口"**：
新建的入口本身就是第四道门的风险（没人会去用你新造的入口）。
**接入已有的、确定会跑的通道**（会话启动 / 提交前钩子 / 定时任务），才是可靠路径。

## 2. 机制二：错误类型字典 —— 每类给三件

**问题**：「下次注意」不可执行。需要的是**可检测特征**（什么时候该想起这条）和**触发动作**（该做什么）。

**格式**（每一类固定三件）：
```markdown
# 类型 N · <一句话命名>

**典型实例**：<真实发生过的一次，含当时的错误结论与真相>

**可检测特征**：
    <我正处于什么状态时，这一类风险最高？ 用「我要做 X ⇒ 我查过 Y 了吗？」的句式>

**触发动作**：
    <具体到可执行的步骤，不是原则>
```

**两个设计要点**：
1. **"可检测特征"必须写成"当下的处境"，不是"抽象的品质"**。
   - ✗ 「要严谨」
   - ✓ 「我要报告『这是缺陷』⇒ 我查过它的注释里有没有写『这是设计如此』吗？」
2. **"触发动作"必须是动作**（跑哪个脚本 / 写哪句话 / 先做哪一步），不是态度。

**⚠️ 类别不要轻易新增**：实测中，把新教训**并进已有类别**（作为"实例"或"子型"）
比新开一类更有效 —— 因为清单越长，被读到的概率越低。
**判据**：**「它的存在会派生其他类别吗？」会 ⇒ 才配新开在最前面；否则追加。**

## 3. 机制三：清单对账钩子（治"答漏"）

**问题**：使用者一条消息列了 14 项，Agent 答了 12 项就收尾。**它自己认为答完了。**
这是**输出截断**：答到"自己觉得够了"就停，**不检查是否答全**。

**做法**：
```
一个"用户提交消息时"触发的钩子：
  ① 从消息里**抽取编号清单**（「1. … 2. … 3. …」或「N 处」）
  ② 若项数 ≥ 阈值 ⇒ **自动提醒**："本消息含 N 个编号项，回复时逐条对账"
  ③ 否则**静默退出**（不打扰 —— 否则它自己会变成噪声源）
```

**为什么必须是钩子，不能是"按需脚本"**：
> **「按需」= 靠自觉**：记得跑 ⇒ 跑；忘了 ⇒ 不跑；不知道 ⇒ 不跑。
> **而这正是要解决的问题本身。**

**配套判据**：**「我已做完 X」≠「我答了 Y」。先数对方有几问，再数自己答了几问。**

## 4. 机制四：派工模板（给委托给子 Agent 的任务）

**问题**：同一个遗漏在多轮委派里反复出现，**因为 brief 是每次现编的**。

**做法**：把 brief 做成**固定句式**，每条都对应一次实伤：

```markdown
## 派工前自问三句
1. 这活是不是已经做完了？（先查版本历史，别信任务清单的状态列）
2. 「喂靶」我有没有写清「**怎么拿**」？（见下）
3. 我给的行号/数字是什么时候读的？（给行号要附「何时读的」）

## 必须逐条写进 brief 的
- **先核实际状态**（版本历史），发现已完成 ⇒ 立刻停下报告，**不要照 brief 重做**
- **喂靶取法**：用 `取历史版本到临时路径` 的方式拿到"已知坏版本"，
  **绝不原地改任何被跟踪的文件**（否则一次命令超时就把"证明"变成"污染"）
- 提交用**只提交指定路径**的形式；提交前核对暂存区
- **断言必须双向夹逼**，不许单向
- **任何"零命中/不存在"的否定结论**，必须换一条不含 `head` 的通路复核
- **未核必须写"未核"**，不许把"判不了"写成结论
- **你认为我给的判断有错的地方 —— 直接说**，附你的实测
```

**⚠️ 最贵的一条是"喂靶取法"**：
一份 brief 只写了「必须拿已知坏版本喂一遍证明它会失败」，**没写"怎么拿"**
⇒ 子 Agent 用原地修改生产文件的方式制造坏版本，**命令超时被移到后台**
⇒ **还原那一步没跑到** ⇒ 工作区留在**被改坏的状态**，且无任何提示。
> **⇒ 要求一个动作，必须同时给出"允许的实现方式"** —— 否则对方会用最直接（也最危险）的那种。

## 4.5 机制四点五：**什么时候该用子 Agent / 团队，什么时候绝不该用**

> 这是**最容易被滥用**的一条。一次实测里主 Agent 派出 7+ 个子 Agent，**同一类遗漏反复出现**，
> 其中最贵的一次（§4 那条"原地改生产文件"）**本身就是派工的产物**。
> 所以下面给的不是"多派几个会更稳"，而是**判据与反例**。

### 4.5.1 先分清五件事，它们常被混成"要不要并行"

| 手段 | 什么时候用 | 一句话判据 |
|---|---|---|
| **独立复核** | 结论会被当作**决策输入**，而产出者就是我自己 | **让一个"看不到我的推理过程、只看最终产物"的主体去查** |
| **并行子 Agent** | 任务能切成**不共享状态**的片 | **若每个子任务都做到最好，它们会碰同一个文件吗？** 会 ⇒ 不能直接切 |
| **独立工作树** | 需要隔离 git 写操作 | **最坏能改到哪个 ref / 索引？** 是当前 HEAD ⇒ 必须换工作树 |
| **后台运行** | 任务长，且**不需要我看中间过程** | 中途需要人判断 ⇒ 后台反而有害 |
| **多 Agent 长期协作** | 任务**跨天**，需要分工 | 先问：**它们共享哪些"热文件"？谁唯一拥有？** |

### 4.5.2 ⛔ **绝不该用**的情况（实测反例）

**① 产出必须"看不见源头"时**（脱敏稿 / 对外发布物 / 对外反馈）
- 子 Agent 要**抽象化**就得**先看到原文** ⇒ **凭空多一个泄漏面**。
- 实测：一次"身份信息被写进提交信息"的事故，正是这类流程里的产物。
- **⇒ 这类活由主 Agent 做**；把复核交给"只看最终产物"的一方（见 4.5.3）。

**② 无法验证"抽象后是否仍然准确"时**
- 那需要**对照原文**，而原文**正是要被隔离的东西**。子 Agent 做不到。

**③ 会凭空多一层"转述"时**
- 每一次委托 = 一次信息传递。**而"未经验证的断言"最主要的入口就是转述**
  （实测一天内同形状 ≥4 次：转述别处给的数字、转述别处给的根因、
  把上一轮的结论抄进唯一账本、把错的根因转给下一个 Agent）。
- **⇒ 转述链越长，这类错误越多。**

### 4.5.3 ✅ **最值得用**的情况：**上下文不对称的独立复核**

> **让复核者只见最终产物、看不到源头与推理过程 ——
> 它能看到的东西**比我还少**，所以它能发现**我看不见的**。**
> （我看不见，恰恰是因为我知道原文。）

```
交给复核者：**最终产物**（文档/代码/结论）+ **一个具体问题**
不给它    ：原始材料、我的推理过程、我的结论
```
**问什么**（每次只问能被回答的）：
- 「这里面有没有任何可能指向**某个具体组织 / 个人 / 项目**的信息？」
- 「它作为一份**独立文档**读得通吗？有没有只在你读过原文时才成立的句子？」
- 「这个结论**在什么输入下会不成立**？」（= §8 的"判据可被空满足"）

**⚠️ 复核者说"没问题" ≠ 它核过** —— **要求它给出方法、看到了什么、怎么得出"没有问题"。**

### 4.5.4 并发咬合的实伤（**按危害排序**）

| # | 形状 | 实测频次 | 缓解 |
|---|---|---|---|
| 1 | **暂存区互相卷走**：A `add` 自己的文件后**不带路径**提交，把 B 已暂存的文件一并提交 | 一天 **4 次** | 用**只提交指定路径**的形式；提交前**核对暂存区文件名与数量** |
| 2 | **共用同一提交身份** ⇒ 事后**无法从作者信息判断归属** ⇒ 主 Agent 的"无缺陷确认"因此失效 | — | 派工时给每个子 Agent **显式设置提交身份** |
| 3 | **多人同时提交触发钩子失败**（钩子报了整库级检查失败，不知道是谁的改动） | 一天 **7+ 次** | 钩子文案必须**指出"是谁的改动出错"**，否则每个看到的人都去重查一个不是自己的问题 |
| 4 | **共享"热文件"被并发改** | — | **先列热文件、指定唯一所有者**；brief 写"要改别人的热文件 ⇒ **停下报告**" |
| 5 | **"按目录划片"是假隔离** | — | 判据见 4.5.1 第二行 |

### 4.5.5 ⚠️ **子 Agent 会重复主 Agent 的错**

- 实测：同一天里**两个不同的子 Agent 各自犯了"单向断言"**（§8 那条），
  **另一个犯了"原地改生产文件"**（§4 那条）。
- **⇒ 原因很简单：子 Agent 不知道你今天学到的教训。**
- **⇒ 所以 §4 的派工模板不是"可选的礼貌"，而是**唯一**能把教训传给下一个执行者的通道**
  （除非你已把教训放进"每次启动自动注入"的通道 —— 见 §1）。

### 4.5.6 主 Agent 对子 Agent 产出的**验收义务**

> **不采信 commit message（或任何自述）。**

实测两例：
- 一个 Agent 报告"已还原被改坏的文件"。**独立用内容哈希核过两侧一致**，才确认是真的。
- 另一个报告"阈值已锁"。查证后发现**常量是对的、但没有任何机制保证它不被改** ——
  **"已锁"当时是一句空话。**

**判据**：**对任何"已验证 / 已修复 / 已完成"，主 Agent 必须能说出"我用什么方法独立核过"。**
**说不出来 ⇒ 那只是转述。**

### 4.5.7 一句话

> **派子 Agent 不是"多一双手"，是"多一个信息传递环节 + 多一个并发写者"。**
> **判据：「这个失误会被谁发现？」**
> **—— 若答案只能是"我自己" ⇒ 派一个"看不到我推理过程"的复核者；
>    若答案需要"看到原文" ⇒ 别派（那是泄漏面）。**

## 5. 机制五：把"可证伪预测"变成带到期日的东西

**问题**：Agent 给出了很好的机制解释并附了预测，**但预测过了核对日就再也查不出**。

**做法（三件一起）**：
```
① 写进落盘文件，**含核对日**与**核对方式**（哪条命令 / 哪条查询）
② 上**一次性定时提醒**（到期那天自动唤回）
③ 提醒内容里带上「**不成立意味着什么**」
   ✗ 「看一眼结果」
   ✓ 「不出现 ⇒ 说明那个修复没生效 ⇒ 回头查，**不要解释成"没有信号"**」
```

**更强的形态：交付"预期会失败"的结果时，必须附决策表**
```
| 现象 | 含义 | 处置 |
|---|---|---|
| 都正常 | 一切正常 | — |
| **报错 X** | **修复在正常工作**（旧代码此时会静默改写并报成功） | **不要回滚** |
| 报错 Y | 上游数据没到位 | 数据齐了之后补 |
```
> **没有这张表，下一个人会把"正确的失败"当 bug 回滚。**

## 6. 机制六：授权边界 —— 不能靠"规则自洽"推导

**问题**：Agent 会用项目内的规则（"可逆 + 不涉及敏感路径 ⇒ 直接做"）去**推导**自己有权执行
某个**外向或不可逆**的动作（对外发布、写生产数据、改配置）。

**实测**：这类推导被**外部权限检查拦下过两次** —— 一次是子 Agent，一次是主 Agent 自己。
**拦下的理由相同**：
> 「这个改动是持久的、而**没有任何一条来自 __人__ 的消息点名它**」

**⇒ 判据一句话**：
> **「这句话是人说的，还是某个 Agent 说的？」—— 后者一律不够。**

### 6.1 ⚠️ **对外发布前的检查：必须扫历史，不只扫工作区**

**实测（就在写这份文档时踩到的）**：
作者改了工作区里的许可证文件（去掉一处不该出现的身份串），**`grep` 工作区 = 0 命中**，
于是认为干净了。**但历史里仍然有** —— 首个提交的那个版本就是旧内容：

```
首个提交的 <file>:3  → <旧内容>      ← 仍在历史里
最新提交的 <file>:3  → <新内容>
```

**⇒ "工作区干净" ≠ "仓库干净"。** 只要那个提交还在，`git show <旧提交>:<file>` 就能取到它，
**任何人也都能取到。**

**做法（发布前逐条做）**：
```
① 冻结回退点（备份 / 记录当前 HEAD）
② 扫**全部历史**，不只工作区：
     git grep -nE '<敏感模式>' $(git rev-list --all) --
   （或对每个历史 blob 做一次扫描）
③ 归类要排除的内容（典型的：身份串 / 本机路径 / 凭据 / 与其它项目关联的痕迹 /
   不该公开的手册 / 大体积生成物）—— **逐类给出"命中数"**，不要只写"查过了"
④ 若命中来自历史 ⇒ **两条路（都不可逆，先备份）**：
     · 历史重写（`filter-repo` 之类）—— 会改变所有下游提交的哈希
     · **若仓库还没有远端、提交很少 ⇒ 直接重建历史最干净**（本文档用的就是这条）
⑤ **重建之后要再扫一遍**（含历史），并确认提交数符合预期
```

**⚠️ 两个容易漏的点**：
- **"不在 HEAD 但 blob 仍在"**：大文件或敏感内容**被删掉之后仍然存在于历史**，
  `.git` 的体积就是证据（实测过一个仓库：`.git` 远大于被跟踪内容的体积）。
- **身份串会从意想不到的地方冒出来**：本文档这次命中的是**许可证的著作权行** ——
  那看起来"本来就该有人名"，但对**不希望把身份与这份文档关联**的作者来说，它同样是泄漏。
  **⇒ 扫描清单要包含"看起来正当"的位置。**

---

**给 Agent 的操作要求**：
- 凡「对外发布 / 写生产数据 / 改权限与配置」⇒ **必须由人显式点名该动作**。
- **被权限拦下时，正确动作是报告，不是换个工具重试**（换工具 = 绕过授权）。
- 同侪 Agent 说"我批准了"**不构成授权** —— 它没有这个权力。

## 7. 机制七：状态的单一事实源 + 两个载体必须同步

**问题**：任务账本里，一条任务的完成状态有**两个载体**（状态列的符号 / 正文里的完成标记）。
做完活只更新后者 ⇒ 按前者判定的消费者**系统性报错**（实测：未收口数偏高，
且**因此派出了已经完成的活**）。

**⇒ 判据**：
> **同一条信息有多个载体时，必须指定唯一事实源，另一个只能是"带检查器的引用"。**
> 且**避免用会兼任修饰的符号表达状态** —— 一个符号两个语义 ⇒ 任何按符号判定的消费者都会读反。

**同类**：日志里的一行"已完成" **不等于** 任务已完成；
**有库表就查库，日志只看过程。**

## 8. 机制八：机制本身也要被验证（**这条最容易被跳过**）

**做法**：
```
① 新写的检查/守卫，必须**拿一个"已知会失败"的样本喂一遍**，证明它**真的会红**。
   ⚠ 喂靶用的"坏版本"必须**从历史版本取到临时路径**，不得原地改文件（见 §4）。
② 断言要守**类别**，不守**形状**（正则扫写法 ⇒ 换个拼写就失效）。
③ **零消费者的检查 = 死代码**，且它的注释会持续说谎。
④ 检查的**输出要与权威源对账**（例如：计数类检查的项数 vs 直接数出来的项数）。
```

**⚠️ 一个反直觉的坑**：**单向断言只能守一个方向，而检查坏掉的方向通常恰是另一个。**
实测：断言写成"误报数 == 0"，而**放宽阈值永远不会产生误报**
⇒ 把阈值放宽 10 倍，断言**仍然全绿**，检查已形同虚设。
**⇒ 用双向夹逼：上下界都要有依据。**

**另一个**：**"判据可被空满足"** —— 检查的条件在目标场景下**恒真**。
实测一天里发现 **7 个**，形状各异（量纲不匹配 / 覆盖率不足 / 有限次重采样返回 0 /
分辨率不足以达到阈值 / 白名单形状 / 终态标记挂在周期任务上 / 翻页不校验完整性）。
> **⇒ 判据：「这个判据在什么输入下会为假？」—— 答不出来，它可能恒真。**
> **⇒ 可操作版本：逐项量通过率。≈100% 的硬检查是候选
>   （但必须逐项读文档 —— 设计上"只观察不拦截"的软检查，100% 是设计如此）。**

## 9. 这套做法的成本与边界（**如实说**）

- **它增加短期摩擦**：每次派工/提交都要过一遍清单。
  实测代价：一天里，文档一致性钩子**拦下提交 7 次以上**，每次都要跑一个修复脚本并多一笔提交。
- **它的收益是非对称的**：大多数时候它只是"又过了一遍"，
  但**偶尔它拦下的是"会让结论变错"或"不可逆"的那种** —— 一次就值回成本。
- **它不解决"不知道"**：它只解决"知道但没做"。
  机制不能替你发现你没想到的方向。
- **它会被自己的成功掩盖**：当机制都生效时，你**看不到它拦下了什么**（因为没发生）。
  ⇒ **别因为"最近没出问题"就删掉它们。**
- **它必须随事实源漂移而自我维护**：阈值、计数、路径都会变。
  ⇒ 凡"会变的数字"都要**由脚本从事实源派生**，并配一个**在漂移时拦提交**的检查。

## 10. 一页速查

| 机制 | 一句话 |
|---|---|
| §0 四道门 | 「它死了/没跑/被截了，谁知道？」答不出 ⇒ 机制不存在 |
| §1 准则注入 | 教训要由脚本**派生**进"每次都会跑"的通道；**禁止手抄** |
| §2 类型字典 | 每类给三件：实例 / **可检测特征（写成处境）** / **触发动作（写成动作）** |
| §3 清单对账 | 用**钩子**而非"按需脚本" —— 「按需」= 靠自觉 = 不做 |
| §4 派工模板 | **要求一个动作，必须同时给出允许的实现方式** |
| **§4.5 子 Agent / 团队** | **派它不是"多一双手"，是多一个信息传递环节 + 多一个并发写者**；判据=**「这个失误会被谁发现？」**；**产出必须"看不见源头"时绝不该派**；最值得派的是**"看不到我推理过程"的独立复核** |
| §5 预测到期 | 落盘（含核对日）+ 定时提醒 + **不成立意味着什么**；预期失败 ⇒ 附**决策表** |
| §6 授权边界 | 「这句话是人说的还是 Agent 说的？」后者一律不够 |
| **§6.1 发布前扫历史** | **「工作区干净」≠「仓库干净」**；必须 `git grep <模式> $(git rev-list --all)`；⚠ 身份串会从「看起来正当」的位置冒出来（如许可证著作权行） |
| §7 单一事实源 | 一条信息多个载体 ⇒ 指定唯一源；符号不得兼任修饰 |
| §8 机制自证 | 拿**已知坏样本**喂靶；断言**双向**；守类别不守形状 |
| §9 边界 | 只治"知道但没做"；成本是短期摩擦，收益是非对称的 |
